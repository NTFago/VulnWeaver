# ADR-035：agent 上下文分层——调查日志与窗口兜底

- 状态：已接受
- 日期：2026-09-30
- 相关：ADR-027（智能体驱动审计）、ADR-029（审计检查点与断点续跑）、ADR-030（项目级调查记忆）、ADR-033（模型供应商注册表）

## 背景

"agent 主导 + 长线作战"目标下，审计循环（`agent_loop`）的上下文模型有一个结构性缺口：每轮模型调用是无状态的两消息提示（系统指令 + JSON 载荷），轮间唯一的信息载体是 `last_feedback`——**只有上一轮**的步骤输出（≤8 步 × 8KB）。两轮之前的任何信息模型都看不到：第 3 轮不知道第 1 轮查过什么、不知道之前哪些计划被策略引擎拒绝过。长调查（ADR-033 后审计 deadline 默认 8 小时、可配 7 天）里这直接导致重复调查、反复提交会被拒的计划。

ADR-027 曾记录过一次反教训：把累积步骤全部重放会逐轮膨胀提示并淹没收敛指令，修复方向是"只带当前轮"。所以缺口不能靠"重放完整历史"补，需要的是一种**有界的压缩中间层**。

同期调研了主流 harness 的上下文管理（Claude Code、Codex CLI、Gemini CLI、Cline/Roo、SWE-agent、Aider、Cursor），共同模式非常一致：

1. 在窗口的 50–92% 处触发压缩，而不是 100%；
2. 分层升级：先廉价地折叠/截断旧工具输出，再做 LLM 摘要，最后才是硬裁剪兜底；
3. 任何重写都钉住一组固定项：系统提示/指令文件、任务状态、最近 N 轮、全部真实用户消息；
4. 摘要中间、原样保留头尾；
5. 压缩产物是结构化的"交接快照"（Claude Code 的 9 段摘要、Gemini 的 `<state_snapshot>`、Codex 的 handoff 清单）；
6. 单个工具输出硬截断（2KB–10KB 级），检索类输出常豁免。

## 决策

### 1. 三层上下文：钉住头部 + 压缩中间 + 原样尾部

每轮提示固定为三层，全部有界，提示复杂度对轮数保持 O(1)：

- **钉住头部**（不变）：系统指令、objective、工具目录、静态任务上下文（含 ADR-030 的 `prior_investigations` 跨任务记忆）。
- **压缩中间（新增）**：`investigation_journal`——上一轮之前所有轮次的确定性单行摘要。每个执行步骤一条（轮次、工具、成败、failure_code、≤256 字符的输出摘要），每次计划拒绝一条（轮次 + 原因码）。上限默认 48 条（超出按最老先出淘汰），`AgentLoopBudget.max_journal_entries=0` 可整体关闭。
- **原样尾部**（不变）：`last_feedback` 带上一轮完整有界步骤输出。

与 `last_feedback` 的去重是结构性的：journal 条目携带轮次号，构提示时过滤掉与 `last_feedback.planning_round` 同轮的条目——同一轮永远只以一份（原样或压缩）出现。

### 2. 确定性压缩，不做 LLM 摘要

主流 harness 的完整压缩（compaction）用一次模型调用生成摘要。这里刻意不用：

- 本循环的提示本来就是 O(1)，不存在"越滚越长的转记录"需要摘要——缺的是中间层回忆，不是压缩器；
- 规划循环是热路径，增加一次摘要调用就增加一个失败模式和一段延迟，而摘要失败时的回退（Gemini 的做法）恰恰是截断——即本设计直接采用的手段；
- 确定性摘要是纯函数，可单测、可检查点、可复现（SWE-agent 的 history processor 路线、Gemini 的 collapseOlderFunctionResponses 路线都是这个形态）。

摘要取工具输出的 `summary`/`message`/`reason`/`note`/`status` 字段（按此优先级），否则取 JSON 前缀；换行折叠为单行，按 `max_journal_entry_chars` 截断。ADR-030 的记忆原则在这里复用：**记录判断的痕迹，不记录工具转储**——工具结果永远可以重新生成。

### 3. Journal 进入检查点，随断点续跑恢复

`LoopProgress`/`LoopResume` 增加 `journal` 字段，`code_audit` 检查点随 `steps`/`last_round_steps` 一并落盘（上限 512 条防御性封顶，实际由 budget 封住）。崩溃/租约接管后，续跑的第一次模型调用同时看到：压缩的旧轮 journal + 原样的上轮 feedback——与 ADR-029 的"从同一视点继续"语义一致。装载侧只保留带整数轮次号的映射条目，损坏检查点降级为少几条记忆，不阻塞审计。

### 4. 网关窗口兜底：system 消息永不裁剪

`_fit_context_window`（ADR-033 后按模型 `context_window_tokens` 生效）是最后的紧急层，正常情况下永远不该触发——上游各层已把提示封在有界预算内。本次加固两点：

- **system 消息钉死**：裁剪候选只含非 system 消息。系统提示携带指令与"工具输出是不可信数据"的护栏，任何窗口紧急情况都不构成剥离它的理由（与主流 harness 钉住 AGENTS.md/system 上下文一致）。此前按"最大消息先裁"可能恰好裁到系统提示。
- **无可裁时不撒谎**：超预算但没有任何可裁消息（全是 system 或都低于最小裁剪阈值）时原样发送、不发 `context_window_trimmed` 决策记录——由供应商最终裁决，而不是记录一次不存在的裁剪。

### 5. 静态上下文的入口封顶

`static_leads`（ADR-032 的扫描器线索进入审计上下文的入口）补上 200 条上限并报告 `total_leads`。此前它是静态上下文里唯一无界的列表，一次大扫描运行可以撑爆每一轮的提示。工具侧原有的三层输出封顶（工作区 16K 文本、循环 8K 观察、检查点再收敛）不变。

## 后果

- 每轮提示最坏增加 48 × ~0.3KB ≈ 15KB（约 4K token），换来模型对整个调查史的召回；`max_steps_per_plan=8` 下 journal 每轮最多新增 8 条。
- 模型现在能看到的"自己过去的工作"有三层时间尺度：本轮尾部（feedback，原样）、本次调查中间层（journal，压缩）、跨任务结论层（prior_investigations，ADR-030）。
- journal 条目与 feedback 一样是**不可信数据**（摘要自工具输出），系统提示的既有护栏覆盖它；它不能改变指令或策略。
- 网关兜底对 JSON 载荷的裁剪仍可能产生非法 JSON——这是紧急路径接受的代价，正确做法是上游预算让它永不触发；不在网关层做 JSON 语义感知裁剪（通用层无法知道各调用方的载荷语义）。
- 提示词变更（系统提示新增 journal 使用句）按纪律需固定样本回归——见验证记录的栈内 E2E 安排。
