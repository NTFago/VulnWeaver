# 与开源项目对比及创新点

> 本报告用于答辩材料，回应大作业要求「通过对比其他开源项目，验证自研系统的创新性」。
> 对比对象：DeepAudit（用户指定主参考）、Semgrep、Ghidra、PentestGPT。
> 口径纪律：本系统能力主张均落到仓库模块/ADR/任务包；DeepAudit 的事实依据为其本地 README 与开源代码；其余项目以「据其公开文档」限定。更新时间：2026-09-11

## 1. 对比维度说明

对比维度按本系统要解决的核心矛盾选取：让大模型智能体参与漏洞挖掘，又不让它失控、让结论可被核查。

- **二进制逆向与解混淆**：题目重点要求，是区分「源码扫描器」与「全链路挖掘系统」的第一分水岭；
- **智能体编排与决策留痕**：差异不在「用了几个 Agent」，而在编排是否可恢复、决策是否可审计；
- **证据链与确认门禁**：大模型有幻觉，防止「模型说有就有」决定系统可信度；
- **动态验证与执行隔离**：复现与利用验证必然执行不可信输入，隔离边界是安全底线；
- **误报过滤**：规则与模型审计都产生噪音，过滤机制决定报告可用性；
- **报告与可追溯性**、**部署与工程化**：交付形态与工程成熟度。

## 3. 逐维度深入对比

### 3.1 二进制逆向与解混淆

DeepAudit、Semgrep、PentestGPT 均不覆盖二进制输入：DeepAudit 依赖清单只有 tree-sitter/Semgrep/RAG 栈；Semgrep 据其公开文档只消费源码文本。Ghidra 覆盖逆向本身——其反编译与 Headless 能力正是本系统直接复用的组件——但它是单点工具：加载什么样本、跑什么脚本、结果如何解读全靠人工，没有「识别壳与混淆后自主规划下一步」的机制。

本系统的二进制管线（T26–T28，`packages/binary-analysis`）把 DIE 壳指纹、平坦化启发式、UPX 脱壳、Ghidra 反编译、angr 定点符号执行纳入固定镜像，由逆向规划智能体（`orchestrator/reverse_planning.py`）基于事实自主决定是否脱壳、是否解混淆、对哪些地址定点分析，决策与理由写入 AgentRun；模型对伪代码做归纳重命名时产出「可读版本」派生工件，原始结果不改写。加壳与未加壳样本因此得到**可追溯的差异化分析路径**，而非固定脚本的无差别输出——这是与单点工具和源码系统的本质差异。

### 3.2 智能体编排与决策留痕

DeepAudit 同样采用 LangGraph 多智能体（开源代码含 agent checkpoint 迁移表），编排能力真实存在；本报告不以此自夸。差异在两点。其一，**工具调用治理**：本系统智能体不直接执行命令，只提交结构化 `ActionPlan`，经 Tool Registry 与 Policy Engine 校验工具、参数、网络、文件系统与资源预算后才分发（`packages/tool-runtime`，T09）；DeepAudit 的沙箱工具由后端 Agent 直接持有 Docker Socket 调用（其 `docker-compose.yml` 注释「沙箱执行必须」）。其二，**编排持久化**：本系统任务消费、Job 租约、结果结算、检查点恢复分别由 ADR-018/019/015/016 约束，Agent 崩溃后可从检查点续跑，决策轨迹可经 `GET /api/tasks/{id}/agent-runs` 逐条复查。这两点让「智能体自主」从演示特性变成可运维、可审计的工程属性。

### 3.3 证据链与确认门禁

传统工具链（Semgrep/Ghidra）只产出「匹配结果」，确认责任完全在人；DeepAudit 用 PoC 验证结果补充 LLM 结论，是有效实践，但其开源数据模型中没有「模型解释不能单独确认」的结构化约束。本系统把证据做成一等公民：每条 Finding 关联 Evidence 多对多关系（supports/contradicts/contextual），证据记录工具版本、镜像摘要、命令哈希与回放配方；`confirmed` 必须满足 `FindingPolicy` 按类别配置的强证据要求（`packages/domain/policies.py`，T15）。该门禁经真实模型验证生效：真实 E2E 中复核模型（GLM）的单独意见只能把 Finding 置为 `unverifiable`。

### 3.4 动态验证与执行隔离

DeepAudit 的沙箱容器隔离参数（禁网、能力丢弃、只读、非 root）本身合格；差异在**控制面边界**：它的后端直接挂载 Docker Socket，后端进程被攻破即接管宿主容器运行时。本系统将动态执行收敛到独立的 Sandbox Runner——全系统唯一连接容器运行时的组件，只接受经 Schema 校验的结构化请求，不接受任意命令字符串、容器参数或宿主机路径（`apps/sandbox-runner`，T18），控制面与普通 Worker 均不挂载 Docker Socket。在此之上，本系统还有 DeepAudit 缺位的模糊测试管线：AFL++ 4.33c/CASR 固定镜像、harness「生成—编译—诊断—修正」有界循环（`packages/fuzzing/harness_pipeline.py`，T32）、崩溃聚类去重与最小化，崩溃证据自动挂接 Finding。

### 3.5 误报过滤

Semgrep 的答案在规则侧（规则精度与 Pro 数据流），DeepAudit 的答案在验证侧（PoC 失败即剔除，README 称验证智能体会自我修正重试）。本系统叠加三层：静态审计与独立复核**强制上下文隔离**（复核不能复述原结论，须独立检查输入可控性、路径可达性、危险操作与保护条件）；模型 finding 必须锚定到 PAIR 函数索引或二进制地址，锚定失败即丢弃不落库（T29 幻觉防护）；最终确认仍受 3.3 证据门禁约束。前两层是区别于对比项目的组合方式。

### 3.6 报告与部署

报告方面，DeepAudit 支持 PDF/Markdown/JSON；本系统输出 Markdown/PDF/SARIF，SARIF 含 `codeFlows` 调用路径（源码为 path:line、二进制为 `binary://0x…` 地址），可进入既有 SARIF 工具链，报告四要素（漏洞、严重等级、证据链、修复建议）与人工复核历史一致（T34）。部署方面 DeepAudit 更成熟（预构建镜像、一键部署、多语言文档、活跃社区），本系统以 compose 最小 9 服务部署为课程演示目标，换取的是 3.2/3.4 所述的边界分离。

## 4. 创新点归纳

1. **源码与二进制统一 PAIR 中间表示，模型结论锚定真实地址防幻觉**。实现：`packages/pair`（源码/二进制双导入器、调用路径投影，T14/T17/T34）。本质区别：DeepAudit/Semgrep 只有源码坐标，Ghidra 只有二进制视角，无统一表示；本系统中模型产出的二进制 finding 锚定不到 PAIR 地址即被丢弃。演示：ELF 样本漏洞详情展示锚定地址与调用链，伪代码视图可对照。
2. **逆向分析步骤由模型自主规划且全程留痕可回放**。实现：T25 规划—执行—观察循环（`agent_loop.py`）+ T27 逆向规划智能体，决策轨迹落 AgentRun。本质区别：Ghidra 人工驱动，DeepAudit 无二进制规划；本系统对加壳/未加壳样本给出差异化、可追溯的规划路径，模型不可用时结构化降级到固定管线。演示：任务页「智能体协作」面板展示逆向智能体的模型、决策数与轨迹。
3. **证据驱动的确认门禁：模型解释不能单独确认漏洞**。实现：FindingPolicy 强证据 + 独立复核上下文隔离（T15，ADR-021）。本质区别：对比项目要么无结构化证据模型，要么允许验证结果直接采信；本系统按漏洞类别要求强证据（如内存破坏须可重复崩溃 + 可控输入），证据不足只能标 `candidate/disputed/unverifiable`。演示：展示一条真实模型复核仅能置为 `unverifiable` 的记录。
4. **控制面/执行面分离的智能体工具治理**。实现：智能体仅输出结构化 ActionPlan，经 Tool Registry/Policy Engine 校验（T09）；Sandbox Runner 是唯一容器运行时入口（T18）。本质区别：DeepAudit 后端直接挂载 Docker Socket；通用智能体框架（MetaGPT/AutoGen 类）也不内置此边界。演示：架构图标注唯一运行时入口，展示策略拒绝的负向用例。
5. **从 Finding 到模糊测试与自动利用的全自动闭环**。实现：复核确认后自动投递 fuzz（harness 生成/编译/修正循环，崩溃证据挂接）与 exploit（模型生成脚本经安全红线校验后沙箱执行，T31/T32）。本质区别：DeepAudit 的验证智能体只覆盖 PoC 脚本层，无覆盖引导模糊测试与崩溃分诊管线。演示：任务页八阶段流水线中「模糊测试」「验证与利用」两阶段的状态与产物。

## 5. 诚实的差距与取舍

**DeepAudit 更成熟的方面**：其一，真实成果——据其 README，其（闭源）版本已获得 49 个 CVE 与 6 个 GHSA、涉及 17 个开源项目，本系统目前以教学样本验证链路，无真实 CVE 产出；其二，产品工程化——RAG 知识库、十余种 LLM 平台与 Ollama 本地部署、一键部署与预构建镜像、三语文档与活跃社区，本系统模型接入当前以 OpenAI 兼容协议 + 双端点（DeepSeek/GLM）实测为限；其三，语言广度——其宣称 10+ 语言，本系统首版固定 C/C++/Python/Java 源码与 x86/x64 ELF/PE 二进制。Semgrep/CodeQL 在规则生态与大规模工程验证上同样远超课程系统。

**取舍原因**：本系统把工程预算优先投在安全边界与结论可信度上——控制面/执行面分离、专用 Sandbox Runner、证据门禁、隔离复核会增加服务数量与链路复杂度（最小部署 9 个服务），但属不可妥协的红线；利用生成刻意停在 L1 级安全证明（受控崩溃、marker 验证），不追求武器化；对比样本采用自建无害教学程序并登记来源授权。这是课程范围内「把边界做对」优先于「把面铺开」的主动选择。

## 6. 结论：差异化定位

现有的开源选择各有强项：Semgrep/CodeQL 把规则做深，Ghidra 把逆向做精，DeepAudit 用多智能体把源码审计做成了有真实 CVE 产出的产品。本系统（VulnWeaver）的差异化定位是：**面向源码与二进制两类授权样本，构建一条「智能体自主规划、结论受证据约束、执行受沙箱隔离」的全链路漏洞挖掘系统**——逆向步骤由模型自主规划且全程留痕，源码与二进制统一到 PAIR 并以地址锚定防幻觉，漏洞必须满足按类别配置的强证据门禁才能确认，所有动态执行收敛于唯一的 Sandbox Runner。一句话概括：对比项目分别回答「扫得准」（Semgrep）、「看得透」（Ghidra）、「审得快」（DeepAudit），本系统回答的是「让智能体参与挖掘时，每一步可信、可查、可控」。
